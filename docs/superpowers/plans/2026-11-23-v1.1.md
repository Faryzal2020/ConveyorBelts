# ConveyorBelts v1.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Apply the v1.1 play-test changes: Q/E flips the L, a buffer-less "pull from anything, push to anything" Pusher, a shared category/search filter tab, short UI text, and conduits under belts and ports.

**Architecture:** The Pusher stops being a belt sink. Each move it resolves one pull source on the cell behind (belt end, items on the cell, a building's `IThingHolder` container, product adapters) and one push target in front (belt, the v1 machine adapters, haul destinations), and transfers only when both agree. A new shared `Section_ItemFilter` drives both ports' filters; the rest are local edits.

**Tech Stack:** C# net10.0 against the installed RimWorld 1.7 `Assembly-CSharp.dll` + Harmony 1.7 (already referenced), xUnit for `Sim/`, RimTestHarness runner for in-game checks.

**Spec:** `ConveyorBelts/docs/superpowers/specs/2026-11-23-v1.1-design.md` (approved 2026-11-23). It overrides `PLAN.md` where they differ.

## Global Constraints

- Branch `feat/v1.1` (exists; design doc committed as `c5c7002`). Every commit includes the rebuilt `Assemblies/ConveyorBelts.dll`; messages end with a blank line and `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- `Sim/` stays free of RimWorld/Unity types. Build 0 warnings; full `dotnet test` passes before each commit.
- Pusher: never pulls a **live pawn**; corpses are ordinary items. Never pushes onto plain ground. New (and migrated v1) pushers start with an **empty filter**. "Pull from forbidden" toggle, default **on**; moved items keep their forbidden state. Items reserved by any pawn are skipped. Not a belt sink.
- Pusher move: every **60 ticks** while powered; amount = min(source count, item `stackLimit`, target room; belt target also ≤ that belt's `MaxStackAt`). Count-based products (barrel beer) move only when the target takes the whole batch (no holding).
- Pull order: belt end → items on the cell → building `IThingHolder` contents → product adapters. Push order: belt → v1 machine adapters (frame, fuel, wort) → haul destination (slot group at the front cell, or an `IHaulDestination` that is also an `IThingHolder`, e.g. graves). No generic container insert.
- Filter tab (both ports): left pane category tree (tri-state) / search results (items + categories, tag, "Allow all" ↔ "Disallow all"); right pane all allowed items with ✕; "All" / "None" for the whole filter. No HP/quality sliders, no special filters.
- Text rule: short labels, no repeats of what the icon/graphic shows, tooltips only where a label alone is ambiguous, "None" for empty values. Exact strings from spec §5 table.
- Conduits: any def with `building.isPowerConduit` may share a cell with belts and ports, either build order.
- One RimWorld instance at a time; always `node runner.js quit 0` (or `stop`) after a check. In zsh call the runner through a function (`r(){ node runner.js "$@"; }`), not `R="node runner.js"; $R`.

## Review Focus

1. **A source stack bigger than the target's room** → only the room's worth moves, the rest stays in the source, total conserved. → Task 4 step 4 (scenario P2).
2. **Barrel beer with a target that can't take the whole batch** (basic belt, max stack 10, vs up to 25 beer) → nothing moves, beer stays in the barrel. → Task 4 step 4 (scenario P5).
3. **Belt behind that points sideways or away** → not a source; its items keep flowing past. → Task 3 step 5.
4. **Item a pawn has reserved** (pawn walking to haul it) → skipped; the pawn's job completes. → Task 4 step 4 (scenario P7).
5. **Category allowed, then one of its items ✕'d** → category shows partly allowed; the removed item stops moving/hauling; the rest still do. → Task 2 step 4.
